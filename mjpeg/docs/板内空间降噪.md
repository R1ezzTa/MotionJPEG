# 板内空间降噪与独立 JPEG（2026-09-28）

本文件保留首版 RGB sigma 降噪的实现、工程结果和用户“不明显”的反馈。当前已上板的第二版采用 YCbCr 中值混合及两级亮度引导色度平滑，见 [板内稳健降噪 v2](板内稳健降噪.md)。下文“当前固件”等描述均指首版实验当时的状态。

按用户要求，当前固件先去掉帧间区域复用及自适应阈值，恢复每帧独立 JPEG，再验证降噪。旧实验源文件、固件、抓包和失败报告作为历史记录保留；当前构建不综合 `jpeg_spatial_skip*` 和双路熵码比较器，不发送 SPJ1/SPJ2，也不读写 DDR3 帧间参考。PC 窗口移除块跳过阈值和自适应控件，改为空间降噪强度。

## 处理方式

数据链路为：`OV5640 RAW8 → BGGR 去马赛克 → RGB 空间降噪 → YUV422 → JPEG → USB`。相机 profile 5、`3820=42` 的偏绿修正和 Q60/Q75/Q85 保持原有设置。

降噪只使用当前帧的 3×3 RGB 邻域，不保存前一帧，也不做时间平均或运动补偿。两行 RGB 缓存和原去马赛克行缓存使用同步读、读前写的 BRAM 模板。第一输出等待一行及一列；反射边界和合成末行保证每帧仍有完整的 1920×1080 像素。

邻域固定权重为：

```text
1 2 1
2 4 2    / 16
1 2 1
```

对每个邻居，只有 R/G/B 三个通道与中心像素的绝对差都不超过强度 N，才让它参与加权；否则用中心像素代替该邻居。三个通道使用同一组通过条件，避免分别选择邻居造成颜色不一致。结果四舍五入到 8 bit RGB。

- `N=0`：像素逐字节保留，仍走相同的行缓存流水线，用于对照。
- `N=8/16/32`：PC 提供弱/中/强快捷值，也可输入 0～255 任意整数。
- 强度增大允许更大像素差参与平滑，可能损失细纹理和低对比边缘；255 接近普通高斯平滑，仅作为范围验证，不能视作推荐画质档位。

这是一种阈值限制的空间滤波，不估计真实噪声方差。它主要针对平坦区域的小幅噪声；极端孤立坏点可能被保留，不能代替相机坏点校正。算法没有历史帧混合，但仍可能平滑物体当前帧的边缘，不能据此宣称画质无损。

强度在降噪输入的 SOF 被接收时锁定，整帧使用同一值；帧内改设置等下一帧。所有有效位、SOF/EOL/EOF、色度奇偶位置和像素数据均随反压一起保持。abort/复位丢弃未完成帧的流水线有效位，行 RAM 不做大规模复位；新帧覆盖数据并按行有效性隔离旧内容。

邻域选择、行内加权累加和最终输出分成流水级；用 9 bit 上下界完成等价的差值门限判断，正确处理 0/255 附近的溢出。各级统一跟随输出反压，每周期仍可接收一个像素，不把整组比较和累加压在同一周期。

## 操作与协议

固件复位默认降噪 0、Q85、停止、关灯。板载 KEY0/1/2/3 继续负责启停、画质、2 秒补光、停止并关灯。PC 开启/停止仍使用同一板卡运行请求。

```powershell
& 'E:/anaconda/123/python.exe' mjpeg/host/camera_viewer.py --denoise-strength 16
```

启动后默认等待点击“开启传输”或 KEY0。窗口可输入强度并应用，也可点击关闭/弱 8/中 16/强 32。查看器根据板卡能力和状态读回开放控件；旧固件或抓包回放禁用修改。PC 不做降噪，也不修改 JPEG 或显示颜色。

USB `Nxx\n` 原子设置两位十六进制强度，例如 `N10\n` 设置 16，`N00\n` 关闭。半条命令不生效，畸形输入排到换行，100 ms 无后续字节则回到空闲；命令体里的 C/S/L/画质数字不会执行成独立命令。物理按键在解析过程中仍可响应。

相机 MBLK type 7 的配置字 bit 10 表示降噪能力，低 9 bit 仍为初始化索引；flags bit 30:23 在此模式下表示降噪请求强度。原帧间能力位均关闭，Txx/A0/A1 被完整消费并忽略。此字段是板卡请求读回，不能当作每个已接收 JPEG 的帧内强度元数据；逐档验收先等状态确认，再开始新传输。

## 构建与验证

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File mjpeg/scripts/run_ddr3_build.ps1 -Action Full -CameraProfile 5 -SkipEnable 0 -ThresholdEnable 0 -AdaptiveEnable 0 -DenoiseEnable 1
powershell -NoProfile -ExecutionPolicy Bypass -File mjpeg/scripts/run_denoise_sim.ps1 -Width 1920 -Height 8
powershell -NoProfile -ExecutionPolicy Bypass -File mjpeg/scripts/run_bayer_sim.ps1 -DenoiseEnable 1 -DenoiseStrength 16
```

独立数值参考使用完整当前帧直接计算邻域，不复用 RTL 的流控或行缓存实现。覆盖 0/8/16/32/64/255、运动边界、末行/末列、反射边界、随机输入/输出停顿、帧内修改设置和 abort 恢复。小图、1920 宽行缓存与 RAW→降噪→YUV 的集成逐像素比较均通过；1920×1080 常量 RGB 信号的整帧像素及标记也核对。已知平坦信号叠加 ±5 噪声的独立模型验证 N16 可降低均方误差，高对比无噪声阶跃在 N16 下保持不变；这些是模型性质，不能当成摄像头真实降噪量。

主机 91 项回归通过，包括新能力位与帧计数/初始化索引共存、设置先于 START、重连恢复设置、旧固件拒绝修改和回放不写板卡。控制器仿真验证 N 命令全范围、原子提交、关闭、超时、畸形命令隔离以及禁用的帧间命令；原三档完整量化表、启停和补光控制回归通过。

首轮综合 `full_20260928_152105` 在布局前停止：独立 JPEG 已移除 DDR3 应用传输，而旧约束脚本强制要求其 Gray 指针和 RAM 端点存在。修正为：活动 DDR3 实验仍严格检查所有端点，独立 JPEG 构建必须确认命令 bundle 和 FIFO RAM 已被移除；公共 DDR3 复位/状态同步及相机/USB CDC 检查继续执行。该失败构建与首版源快照保留在 `work/denoise_20260928/first_source_snapshot/`，不视为通过固件。

第二次 `full_20260928_152815` 完成布线但未生成 bitstream：组合的邻域绝对差、筛选与累加造成 WNS −0.583 ns、TNS −22.130 ns。改为上述流水级后重新构建和逐像素验证。此次还检出 MIG 的 `rstdiv0_sync_r_reg/PRE` 公共复位入口；核对本地厂商 `mig_7series_v4_2_infrastructure.v:713`，它与原先已审核的 `rst_sync_r`/`rstdiv2_sync_r` 一样，异步置位、在目标时钟上逐级移出零以同步释放。仅把这一具体复位寄存器入口纳入审核，其他未知 Critical CDC、setup/hold 和 bus skew 仍会阻止出片。失败报告和源快照 `bram_source_snapshot/` 保留。

第三次 `full_20260928_154712` 时序通过（WNS +0.052 ns、WHS +0.012 ns），但实板首帧严格解析报 `JPEG boundary`，未通过传输验收。原因是 `mjpeg_synth_top` 仅根据 DDR 参数选用了 SPJ 的单字节打包器；独立 JPEG 编码器输出多字节 beat，被错误截为一个字节。使用 `SPATIAL_DDR=1, SPATIAL_SKIP=0` 的端到端控制仿真复现同样错误。改为只有启用 DDR 帧间算法才选单字节打包器，独立 JPEG 使用原有多字节打包器；修正后六帧、三档画质逐字节匹配黄金 JPEG，三轮 START/END 均通过。新增回归入口 `run_board_controls_sim.ps1 -SpatialDdr 1`。失败实拍保存在 `denoise_sweep_20260928/`，最终验收使用另一个目录，不覆盖失败证据；该候选固件也不视为完成版本。

实板逐档检查入口（关闭预览后运行）：

```powershell
python mjpeg/host/denoise_sweep.py --strengths 0,8,16,32,64,255,0 --seconds 4 --output mjpeg/reports/ov5640/denoise_trial
```

检查每帧独立 JPEG、尺寸、完整量化表、帧号/时间戳连续、最长间隔、FIFO 溢出及清洁 START/END，并保存完整 USB 抓包和各档第一帧 JPEG。带宽为 JPEG 图像载荷，不包含外层 MBLK/USB；各档顺序拍摄，输入像素不完全相同，需要结合首尾 N0 的变化和运动画质判断收益。

## 最终上板结果

完成版本为 `mjpeg/reports/ddr3/full_20260928_155726/davinci_mjpeg_board_test.bit`，SHA256 为 `89a4ca0f7f8d2ba9410e9416ce9f0b39ff9200d99ef58e507acfa86622fb2bc8`。2026-09-28 已通过 JTAG 写入当前板卡 FPGA SRAM，CRC ERROR=0、DONE=1、EOS=1；没有写 SPI Flash。源快照为 `work/denoise_20260928/final_source_snapshot/`，安装和验收汇总在 `mjpeg/reports/ddr3/denoise_acceptance_20260928/`。

最终 WNS +0.064 ns、WHS +0.032 ns，TNS/THS 均为 0；setup/hold、DRC 无错误、USB T 释放和 bus skew 检查通过，唯一 Critical CDC 组为上述已审核的 MIG 公共复位入口，没有 DDR3 应用 FIFO 数据跨域。布线后使用 LUT 17654（84.88%）、FF 20491、BRAM36 等效 28、DSP 43。

## 现场画质反馈与不足

用户最新反馈为“现在的噪点在肉眼看来并没有改善”。因此当前算法的视觉降噪效果不合格，载荷下降仅是编码大小证据，不能替代视觉验收，也不能把全部下降量归因于有效噪声去除。下面此前对压缩预览的细碎颗粒判断只是观察记录，不作为现场效果通过的依据。

进一步用独立数值参考核对了两个构造例子：平坦背景 RGB 为 (120,120,120)，中心偏红噪点为 (200,120,120)，N32 的中心输出仍是 (200,120,120)，因为所有邻居被排除后都替换为噪声中心；N255 只降到 (140,120,120)。若中央整个 3×3 区域为 (160,120,120)，它的中心在 N32/N255 下都完全不变，说明小窗口保留较大相关色斑的能力限制。这是算法反例，不是摄像头真实噪声测量。记录位于 `work/denoise_20260928/filter_limit_examples.json`。更稳健的中心估计/中值去孤立点、较大邻域的色度滤波需要另行实现和视觉验证，当前固件没有完成这些升级。

用户随后反馈“感觉开到 32 噪点还是很多”，因此本轮不能把降噪视觉效果标记为已接受。安全创建并只查看一次 760×906、约 104 KB 的实拍对照预览，包含 N0/N32/N255 的缩略图与中心 1:1 局部：N32 的细碎颗粒有所减少，但暗处/柜面的粗颗粒和彩色斑驳仍明显，边缘有软化；N255 仍有残留，额外清理有限。纯文字观察保存在 `work/denoise_20260928/noise_visual_observations.txt`，不把顺序拍摄的局部对照当作噪声真值或硬件故障诊断。

强度改变的是邻居色差门限，固定的 3×3 邻域不随强度扩大。中心噪声较大时，邻居被排除后又替换为中心，可能保留孤立噪点；空间相关、较大范围的色彩噪声也不容易被小邻域去掉。N32→N255 的本次载荷仅再减少约 3%，说明盲目加大同一门限的额外收益有限。

此前颜色诊断实读 `350B=248`、达到当时配置上限，当前对照实拍也较暗；这是优先核对照明/曝光/增益的线索，不代表本轮已重新读出实时增益。下一步先用同一 N32 场景对比短暂补光；若亮时噪声明显减少，应优先处理增益和照明。滤波升级则考虑亮度保边、色度使用较大邻域的分开处理，继续保持当前帧内算法；当前尚未实现该升级，也未重新引入帧间算法。
