# 实时压缩帧率与数码管

最新固件已兼容完整分辨率渐进测试，实际完成 VGA、720p、1080p，结果与新命令见 [分辨率渐进上板测试](分辨率渐进上板测试.md)。下文保留小图模式的计数定义及当时测试结果。

板载六位数码管显示 FPGA 最近一个完整一秒窗口内的成功压缩帧数，例如 `000338` 表示 338 fps。每秒更新一次，空闲完整一秒后显示 `000000`。从启动到首次采样期间显示零；停止落在某个窗口中间时，该窗口仍会报告停止前完成的帧数，随后完整空闲窗口才归零。

`rtl/common/frame_rate_meter.v` 使用板载 50 MHz 时钟计数 50,000,000 个周期作为一秒；窗口末尾同一周期的事件计入当前窗口。独立统计输入首像素握手、成功输出帧、失败输出帧和成功输出累计数。成功输出事件定义为原 MJPEG 封包器的整帧末尾描述符被板级传输模块接收且 status=0，每帧只计一次，失败帧不计入压缩帧率。此值反映当前编码与输出链路的实际吞吐，包含 USB 阻塞带来的等待；它不是仅 DCT 核的极限速度，也不是主机解码或显示帧率。

`rtl/top/davinci_fps_display.v` 将同一份压缩帧率转为六位十进制，保留前导零，超过 999999 时数码管饱和为 `999999`，USB 保留完整 32 位计数。六位共阳数码管的位选、段选均为低有效；每位约 1 ms，位切换先关闭全部位选，再建立段码再开启下一位，十进制小数点关闭。`seg_sel[0]` 对应最右侧个位，`seg_led[0:6]` 对应 a–g，bit7 对应小数点。约 6 ms 扫描全部六位。

## 连续模拟图像

USB 命令 `G` 保留原有九帧测试；`C` 连续循环灰度渐变、彩色噪声和彩色平面三种图案；`S` 请求在当前帧完成后停止。连续模式仍使用原像素 ROM 和实际 MJPEG 编码器，每帧重新配置量化表，因此当前小图帧率不能外推为真实分辨率摄像头性能。传输结束后需要主机持续读取，USB FIFO 满时会阻塞编码输出并使测得帧率下降。

在 HDL 工作区的 PowerShell 中，下载后运行：

```powershell
./mjpeg/scripts/run_mjpeg_board_test.ps1 -Action Program
python ./mjpeg/host/board_test_receiver.py --ftdi --live --duration 60 --output ./mjpeg/reports/mjpeg_board_test/live_new
```

主机每秒打印 FPGA 输入帧率、压缩帧率、失败帧率与累计数，`compression` 的整数与数码管一致。到指定时间自动发送 `S`，继续收完最后一帧，并等待两个完整空闲窗口；程序正常结束时数码管显示零。全部 JPEG 都逐字节比对并独立解码，连续模式只保存前三帧图像，所有帧元数据写入 `frames.json`，统计写入 `fps.json`，原始 USB 数据写入 `usb_capture.bin`。

重新运行时先按板上的 RESET，或者重新下载，使帧 ID 归零；已知起始帧号时可用 `--first-id N` 接续。运行期间不要复位。Ubuntu 使用同一程序，指定实际 Linux D2XX 库路径，例如 `--library /usr/local/lib/libftd2xx.so`；当前硬件验证在 Windows 完成，Ubuntu 尚未实测。

## USB 统计协议

原有 JPEG 总线字仍按五字节 `{LE32 data, flags}` 传输。帧率快照在任何完整总线记录之间插入，可能位于 JPEG 封包内部；主机先剥离统计再将原总线字交给 JPEG 接收器。每份快照为连续六条记录，共 30 字节：

| flags | LE32 data |
| --- | --- |
| 0x80 | ASCII `FPS1`，数值 0x31535046 |
| 0x81 | 从复位起递增的一秒窗口 ID |
| 0x82 | 输入帧数 |
| 0x83 | 成功压缩帧数，数码管显示值 |
| 0x84 | 失败帧数 |
| 0x85 | 成功压缩累计数 |

USB 长时间堵塞时保留最新尚未发送的快照；正在发送的六条记录始终保持同一窗口的数据。窗口 ID 可用于识别被跳过的统计窗口。数码管由 FPGA 独立刷新，无需主机计算帧率；实际编码吞吐仍受下游读取能力影响。

## 验证

```powershell
./mjpeg/scripts/run_mjpeg_board_sim.ps1
python ./mjpeg/host/board_test_receiver.py --capture ./mjpeg/reports/mjpeg_board_test/simulation_fifo/usb_capture.bin --sessions 2 --fps-expected ./mjpeg/reports/mjpeg_board_test/simulation_fifo/fps_expected.csv --output ./mjpeg/reports/mjpeg_board_test/simulation_fps_verified
```

外设测试覆盖末周期事件、成功/失败分离、空闲归零、复位、六位十进制转换、饱和、段码极性、位序与位选互斥。完整 FIFO 仿真包含阻塞、握手和总线时序，18 帧实际编码结果与参考一致，并逐条核对 USB 快照与独立统计事件。仿真缩短窗口以减少运行时间，硬件窗口始终为 50 MHz 下的一秒。

## 2026-09-18 实际上板结果

已通过 JTAG 下载到实际达芬奇 A35T，配置状态 CRC=0、DONE=1、EOS=1。构建目录为 `reports/mjpeg_board_test/build_20260918_102230/`；bitstream SHA-256 为 `4739439b45c0eac7699c77ca1c2c457a04dae344ee7af5afe76d2eaf0fc940c0`。50 MHz 路由后 setup slack +7.148 ns、hold slack +0.049 ns，DRC 0 错误、66 个原有 RAM/DSP 警告；资源为 10,400 LUT（50%）、17,011 FF（40.89%）、26 BRAM（52%）、42 DSP（46.67%）。原复制的 19 个 Verilog 和 3 个头文件哈希仍完全相同。

实际回读共 16,526 帧：九帧模式 27 帧，90 秒连续模式 14,255 帧，优化主机记录读取后的 10 秒接续模式 2,244 帧。全部 JPEG 与参考逐字节相同，元数据和帧 ID 连续有效，时间戳严格递增，全部经 Pillow 解码。两次连续测试的 USB 各窗口输入数、压缩数之和均与实际帧数完全一致，失败数始终零，停止后两个窗口输入和压缩帧率均归零，最终累计数 16,526。

最终主机版本的短时实测完整运行窗口为 210–221 fps，平均约 215.6 fps；先前较慢的主机读取方式为 150–179 fps。这些结果仅代表当前三种小图、配置加载、调试封包和异步 USB 回读共同决定的吞吐，主机解析开销与下游阻塞会影响它，不能与真实摄像头分辨率的帧率等同。数码管应显示同一窗口的 `000210`–`000221` 等整数，停止后 `000000`。

证据为构建目录内 `HARDWARE_FPS_PASS.txt`、`fps_hardware_evidence.json`，以及 `hardware_fps_batch_20260918/`、`hardware_fps_live_20260918/`、`hardware_fps_live_final_20260918/` 中的 `VERIFY_PASS.txt`、`frames.json`、`fps.json`、`run_evidence.json` 和原始 USB 数据。数码管驱动、位序与极性已通过仿真，实际显示外观尚待现场确认；用户当前不在板卡附近。板上保留新固件，已停止连续编码，实际报告帧率为零。
