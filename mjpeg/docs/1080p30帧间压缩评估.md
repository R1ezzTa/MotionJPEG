# 1080p30 帧间压缩评估

初始评估日期：2026-09-26。用户确认最终性能目标为单路 1920×1080、30 fps。2026-09-27 已按用户选定的同坐标区域比较实现精确块复用实验，实板 690 帧验收通过；噪声场景无净带宽收益，默认普通 MJPEG。最新实施与测试结论见 [空间块跳过实验](空间块跳过实现.md)。以下保留方案背景，摘要和阈值均未用于本次实现。

后续按用户要求加入运行时可调死区（0～255，反量化 DCT 系数差）；上述“未使用阈值”描述属于此前精确比较基线，当前模式和最终安装状态以 [可调阈值实验](空间块跳过可调阈值.md) 为准。

## 当前基线

当前是逐帧独立 Baseline JPEG（MJPEG），没有参考帧、运动估计或帧间残差编码。摄像头采集保持 1080p30；节省带宽应在 FPGA 到 USB 输出之前完成。PC 收到 JPEG 后再转成 H.264，只能节省后续存储或网络带宽，不能减少板卡到 PC 的 USB 带宽。

[板载控制测试](../reports/ov5640/board_controls_20260926_204800/summary.json)中，各档均约 30.001920 fps；Q85 平均 546,572.68 B/帧，对应 JPEG 负载约 16.40 MB/s。该结果仅适用于当时场景，不能作为任意画面的恒定码率。

[当前路由后资源](../reports/mjpeg_board_test/build_20260926_204044/utilization.rpt)：15,728/20,800 LUT（75.62%），BRAM 29/50（58%）。现有路径使用行缓存和 FIFO，没有集成 DDR 整帧缓存。

## 可以利用的帧间关系

| 方法 | 传输内容 | 成本与适用范围 |
| --- | --- | --- |
| 区域复用/块跳过 | 完整刷新帧；其余帧发送变化块和未变化块的复用信息 | 固定摄像头、局部运动时值得优先评估；噪声、曝光变化和摄像头移动会降低收益 |
| 同位置帧差 | 当前像素与参考帧同位置像素的残差 | 比块跳过更细致，但运动会产生大残差；需要参考像素缓存及一致的重建规则 |
| 运动补偿预测 | 在参考帧中找到匹配块，发送运动向量和剩余残差 | 可压缩移动物体；需要运动搜索、参考图像读取、残差编码及编码端重建 |
| 标准 H.264 编码 | 标准 I/P 帧码流 | 解码兼容性好；需要较大架构改动，现有 JPEG 不能直接增加 P 帧变成 H.264 |

运动补偿属于 H.264/AVC 等标准的核心技术，参考：[Fraunhofer HHI 运动补偿预测说明](https://www.hhi.fraunhofer.de/en/departments/vca/research-groups/video-coding-technologies/research-topics/past-research-topics/multi-frame-motion-compensated-prediction.html)。

1080p 单张 8 位亮度参考图像需要 2.0736 MB，YUV422 需要 4.1472 MB；A35T 全部 BRAM 仅 1,800 Kbit（225 KiB，且其中包含校验位），当前还已经占用 58%。因此全分辨率参考像素不能直接放入片内 BRAM。板卡资料列有外部 DDR3，但 MIG、缓存仲裁与实板时序需要实际集成验证。[AMD DS180](https://docs.amd.com/api/khub/documents/2LByHkO~nSZXcei2D55fTg/content)

## 优先建议：先评估块跳过

保留现有 MJPEG 作为基线，先用离线连续帧测量静止、局部运动、全画面运动及补光/曝光变化时的变化块比例、重建误差和预计传输开销，再确定是否实现。

若结果支持实施，可设计独立的区域更新协议：起始完整刷新；每个采集周期仍保留 30 fps 的帧号和时间戳；未变化区域复用 PC 端上一张已完整重建的图像，变化区域独立编码并传输。块大小、变化判断方式及刷新间隔属于待测参数。

FPGA 可研究只保留块签名或摘要、PC 保存整帧的方案，避免首先引入完整参考像素缓存。但摘要不等于精确的像素比较：哈希有碰撞风险，均值等摘要可能漏掉细节变化，阈值判断可能造成小运动停滞。必须用完整刷新和误差检查约束这些问题，并针对当前噪声实测收益。

区域码流必须具备独立解码边界和明确的 DC 预测状态。不能直接从完整 JPEG 中删除未变化 MCU，也不能把不同帧中任意 JPEG 字节块直接拼接。需评估复用 DCT/量化/Huffman 的代价，控制区域头、共享表和频繁启动的开销；区域太小可能比原 MJPEG 更费带宽。

复位、USB 重连、画质切换、丢失更新帧、解码失败和明显场景变化时，清空旧参考状态并重新完整刷新。只在整帧更新验证成功后提交参考状态；不能让失败帧成为后续复用依据。周期性完整刷新作为恢复保障，具体周期以码率与恢复时间实测确定。

这种协议属于自定义视频传输格式，现有 Python 接收与显示也需要修改，不再保证每一帧都是可单独打开的 JPEG。保存图片时应保存 PC 重建出的完整画面。

## 后续运动预测的边界

用户已要求本阶段不考虑运动补偿，块跳过没有收益也不自动扩大到运动搜索。本段仅保留将来方案的技术边界：DDR 单参考帧、整数像素、固定块、小搜索范围和 I/P 结构需要另行评估。不能只用原始上一帧作为有损预测参考：编码端和解码端必须使用一致的重建参考，否则误差会随帧累积。现有编码器没有完整的反量化/反变换重建环，资源和时序需重新估算。

验收应同时报告 1080p30 实际采集/重建帧率、JPEG 基线与新协议的有效负载及 USB 总字节量、画质误差、延迟、丢帧和参考恢复情况。用同一连续输入及相近画质比较，不提前承诺固定压缩倍数，也不通过减少运动画面的更新帧率冒充压缩收益。当前偏色与噪声仍需要处理，它们会影响变化判断和帧间压缩效果。
