# 空间块跳过实验

2026-09-27 后续新增运行时可调死区。本文记录阈值为 0 的精确复用基线，最新交互、算法和安装状态见 [可调阈值实验](空间块跳过可调阈值.md)。本文“当前板卡已恢复”的描述属于此前精确复用验收结束时的状态。

最终目标：单路 1920×1080、30 fps。用户选定比较两帧中画面坐标相同的区域，本阶段不做运动补偿，也不使用像素差异阈值。

## 比较与重建方式

当前 YUV422 每个 MCU 对应 16×8 像素，4 个 MCU 构成一个 64×8 像素区域。1080p 每行 30 个区域，共 135 行、4050 个区域。JPEG 新增 DRI=4 和 RST0～RST7 标记，在区域边界重置 DC 预测并对齐熵码字节；DCT、采样和量化保持原有算法。

新增 `rtl/video/jpeg_spatial_skip.v` 按区域编号选择对应缓存。比较的是同坐标区域独立编码后的完整内容，不是相邻区域，也不是任意 JPEG 字节偏移。长度及每一个编码字节都相同时才发送 COPY；否则发送 DATA。没有哈希碰撞或变化阈值判定。编码内容相同可准确还原当前 JPEG 的该区域，传输复用不增加现有 JPEG 的量化损失。

第一次和周期性刷新帧全部发送 DATA。帧号失步、配置或量化表改变、核心复位和采集 abort 后重新完整刷新。板载启停会重新配置量化表，因此每个新 START 会建立新的完整参考。

第一版只缓存 192 个区域，每个最多 256 字节，间隔 21 个区域取一个缓存位置，约占 48 KiB。选取位置由区域编号决定，始终对应相同画面坐标；超出容量、长度超过 256 字节或没有参考的区域直接发送。缓存区域发送新内容后保存新参考，不一直对照第一帧。

输入与输出使用两个 8 KiB 区域缓冲，交替接收和发送，避免把整帧存入片内 RAM。只有 192/4050 个区域（约 4.74%）具备板端缓存，其余区域继续原样传输；这属于资源受限的第一版，不是整帧全区域缓存。JPEG 编码仍对整张画面执行，本版主要评估传输带宽，不声称降低 DCT 运算量。

## SPJ1 传输内容

SPJ1 放在原 MBLK JPEG 负载内，MBLK 的帧号、START/END 和描述符结构继续使用。原 JPEG 模式默认不启用此功能。

| 字段 | 格式 |
| --- | --- |
| 帧前缀 | `SPJ1`、keyframe u8、reference frame ID LE32（刷新帧为 FFFFFFFF） |
| JPEG 头 | tag=0、length LE16、完整头（含 DRI、DQT、DHT、SOS） |
| DATA | tag=1、spatial index LE16、length LE16、完整区域熵码及其末尾 RST/EOI |
| COPY | tag=2、spatial index LE16，复用参考帧对应区域 |

每帧全部区域按编号出现一次，未传 DATA 的区域必须有 COPY。PC 校验参考帧号、配置头、区域顺序、RST 循环、区域数量和 EOI，成功后才提交新参考。组装得到标准完整 JPEG 后仍用 Pillow 解码，避免几千次小图解码。描述符长度核对传输负载长度；`Frame.length` 和 `Frame.jpeg` 对用户返回重建后的 JPEG 长度及字节。实际 USB 流量通过 `wire_bytes` 和空间统计里的 `transport_bytes` 评价。

`host/spatial_jpeg.py` 提供精确的编码参考和接收重建；查看器及 MBLK 接收器支持新旧两种负载。`collect_frames=False` 模式只统计原传输负载，不执行空间重建，不能将其描述符长度冒充重建 JPEG 大小。

## 试验入口与证据

构建实验固件：`scripts/run_mjpeg_board_test.ps1 -Action Build -CameraProfile 5 -SpatialSkip`。标准固件省略 `-SpatialSkip`。通用核心默认 `RESTART_MCUS=0, SPATIAL_SKIP=0`；空间模式需使用 `RESTART_MCUS=4` 且彩色宽度为 64 的倍数，灰度宽度为 32 的倍数。当前相机各正式尺寸符合这一要求。

仿真：`scripts/run_spatial_skip_sim.ps1`，独立验证重启编码、空间复用、局部变化、画质切换、随机反压、启停及完整 1080p 吞吐。主机单元测试包括丢失参考、坏包不提交参考、配置刷新和 MBLK 描述符长度。

离线实景分析：`tb/analyze_spatial_capture.py`。它解析原 JPEG 的量化系数，再按重启边界编码，不经过像素解码后重新有损压缩；对照独立解码器验证 RGB 像素完全一致。此工具是离线实验，不是现有固件已经节省 USB 流量的证据。

[历史实景连续 6 帧试验](../reports/ov5640/spatial_offline_20260927/summary.json)：原 JPEG 合计 3,255,129 字节；增加重启分段与 SPJ1 后 3,480,123 字节，净增加 6.91%。即使使用 PC 完整参考缓存，后续每帧也没有一个区域可精确复用。这仅覆盖当时的噪声场景和短样本，但说明现有画面不适合直接承诺严格块跳过的带宽收益。

## 最终验证与当前板卡状态

双缓冲实验构建为 `build_20260927_161013`：路由后 LUT 16402/20800（78.86%）、BRAM 45.5/50（91%）、DSP 44/90；setup WNS +0.064 ns、hold WHS +0.019 ns，构建检查通过。资源报告和时序见该构建目录。

[完整 1080p 仿真](../reports/mjpeg_board_test/simulation_spatial_double/spatial_throughput.json)的两帧均与独立参考 JPEG 逐字节一致，理想连续输入吞吐约 42.26 fps。第二帧相同画面复用了 190 个可缓存区域。该数字是仿真编码能力，不是相机实际采集帧率。随机反压、小范围变化、画质切换和启停仿真通过；主机 41 项测试通过。

[实板最终验收](../reports/ov5640/spatial_double_fast_hardware_20260927/summary.json)接收并独立解码 690 帧，Q60/Q75 各 120 帧、Q85 450 帧，三档均约 30.001875 fps；帧号连续，FIFO 溢出 0，两次 START/END、完整量化表切换及补光自动关闭读回通过。本轮通过 USB 兼容命令验证同一控制器，未重新声称人工按键或灯光外观验收；此前用户已确认物理按键和 LED。

690 帧共有 2,794,500 个区域，只复用 32 个（约 0.00115%）；含重启标记的重建 JPEG 共 308,888,590 字节，SPJ1 负载共 322,868,858 字节，协议负载净增加约 4.53%。这里的对照已经含 DRI/RST，不能把它当作相对原普通 JPEG 的全部开销。与原 JPEG 的同输入比较仍以前述离线 6 帧净增加 6.91% 为准；前后两次实板场景并非严格同输入，不据此计算精确压缩率。

保留失败记录：单缓冲版吞吐停顿导致实板采集溢出；双缓冲第一次验收仍失败，排查发现主机逐字节 Python 扫描 JPEG 阻塞 USB 读取。改为批量搜索标记、接收与独立像素解码分开后，最终 690 帧通过。相关失败报告分别为 `spatial_hardware_20260927` 和 `spatial_double_hardware_20260927`，不能引用为通过证据。

当前板卡已恢复到已验证的标准 1080p30 构建 `build_20260927_160043`，空间块跳过关闭；该构建实板 690 帧全部解码、零溢出。恢复时核对归档 RTL、量化表和约束的 SHA256，并核对 bitstream，JTAG DONE/EOS/CRC 检查通过。恢复后 PC 查看器另做 5 秒检查，141 帧全部解码、约 30.001874 fps、无溢出，空间统计为 null。随后只读状态确认板卡停止、补光关闭，继续由 KEY0 开启。[下载后状态记录](../reports/ov5640/spatial_double_fast_hardware_20260927/installed_after_test.json)含构建、bitstream SHA256 和检查证据路径。

结论：同坐标精确复用功能已实现，当前噪声场景没有净带宽收益。继续使用标准 MJPEG，不减少帧率、不自动加入变化阈值，也不扩大到运动补偿。本实验不能单独判断摄像头噪声的硬件或配置成因。
