# 分辨率渐进上板测试

测试固定彩色 YCbCr 4:2:2、quality=85 量化表，依次运行 640×480、1280×720、1920×1080。板内 `board_test_gradient.v` 按坐标生成像素，保留 ready/valid 握手和两周期一像素的输入节奏，不存储完整帧。算法、行缓存以及最大行宽 1920 配置沿用已有编码器。

测试图样是可复现的周期彩色渐变：Y=(3x+2y) mod 256，Cb=(x+y+80) mod 256（偶数 x），Cr=(floor(x/2)+3y+160) mod 256（奇数 x）。三档使用相同图样公式和量化表，JPEG 大小依次为 77,189、230,246、516,557 字节。CPU 独立整数 JPEG 模型生成参考；全高清参考同时与既有 FHD 测试向量完全一致。参考文件只在主机上使用，板卡输出由实际编码器生成。

## 运行

在 HDL 工作区的 PowerShell 中：

```powershell
python ./mjpeg/scripts/generate_progressive_refs.py
./mjpeg/scripts/run_mjpeg_board_test.ps1 -Action Build
./mjpeg/scripts/run_mjpeg_board_test.ps1 -Action Program
python ./mjpeg/host/progressive_test.py --ftdi --seconds 30 --min-frames 6 --output ./mjpeg/reports/mjpeg_board_test/hardware_progressive_new
```

程序依次发送 V、H、F，分别选择 VGA、720p、1080p 连续图像。每档至少运行指定秒数并接收指定最低帧数，再发送 S，在当前帧结束后停止。收到 END1 后继续读取两个完整空闲窗口，确认输入和压缩帧率归零，随后切换下一档。每帧 JPEG 逐字节比对参考并由 Pillow 完整解码，检查尺寸、状态、连续帧号和板内时间戳。第一帧 JPEG 和解码 PNG 每档各保存一份，所有帧的元数据、耗时和每秒统计均保存。

测试开始预期帧号为零，重新下载或按 RESET 后运行。若接续已知累计帧数，指定 `--first-id N`。主机分块读取 USB，减少每个五字节总线字调用驱动及写文件的开销；测试结果仍包含异步 FIFO、调试封包、主机接收速度带来的限制。Ubuntu 可指定 Linux D2XX 的实际库路径，当前实际硬件测试在 Windows 主机进行。

## 测量口径

- `start_interval_fps`：按相邻帧首像素的 FPGA 时间戳计算平均吞吐，公式为 (帧数−1)×50,000,000/(末帧时间戳−首帧时间戳)。支持低于 1 fps 的小数结果。
- `mean_feed_ms`：从首像素握手到末像素握手的平均时间，包含输入因行缓存或下游阻塞而等待的时间。
- `mean_jpeg_end_ms`：从首像素到最后 JPEG 数据字被板级串行化模块接收的平均时间。
- `mean_descriptor_end_ms`：从首像素到完整帧描述符最后一个字被串行化模块接收的平均时间，是每帧实际编码和输出链路耗时；这些指标没有隔离 USB 背压，不能称为编码核独立计算耗时。
- `input_wait_fraction`：输入 valid 为真而 ready 为假的周期数占输入跨度的比例。
- `output_wait_fraction`：封包输出 valid 为真而 ready 为假的周期数占首像素到描述符结束跨度的比例，包含固定五字节串行化和 USB 写入等待。
- `wire_expansion`：捕获调试链路字节与 JPEG 有效字节之比，包括封包、统计和停止标记。

板载数码管仍每秒显示最近一秒内成功完成的整数帧数。平均 0.6 fps 时，它会在 `000000` 与 `000001` 之间变化；零表示该窗口没有完成一帧，不能单凭这个值判断编码停止。主机使用明确结束标记判断当前帧是否收完，再确认空闲归零。

每帧检查输入跨度−输入等待周期=2×(宽×高−1)，结合参考 JPEG 完全一致，验证实际覆盖完整帧的像素数量。每档的一秒窗口输入数、压缩数之和分别与已验证帧数一致；末尾累计成功数与连续全局帧号一致。

## 逐帧统计协议

原有 FPS1 统计保持兼容。大图每帧在描述符之后增加七条五字节记录：flags=0x90 是 TIM1（LE32 0x314d4954），0x91 是帧 ID，0x92–0x96 分别为输入跨度、JPEG 结束跨度、描述符结束跨度、输入等待、输出等待（50 MHz 时钟周期，32 位无符号）。这些跨度以首像素为零。停止后 flags=0xa0、LE32 数据为 END1（0x31444e45），表示当前流已结束，主机可以重新等待 MJBT 前导。

## 仿真

```powershell
./mjpeg/scripts/run_progressive_sim.ps1
python ./mjpeg/host/progressive_test.py --capture ./mjpeg/reports/mjpeg_board_test/simulation_progressive/progressive_capture.bin --simulation --timing-expected ./mjpeg/reports/mjpeg_board_test/simulation_progressive/timing_expected.json --output ./mjpeg/reports/mjpeg_board_test/simulation_progressive_verified
```

控制链路仿真将三档尺寸缩为 48×16、64×24、96×32，共六帧，检查像素、光栅标记、阻塞、帧边界停止、结束标记和 USB 解包，并将每个 TIM1 值与测试台独立时钟统计逐条对比。发生器另外检查全部 1920 列及 0/479/719/1079 行的坐标运算。完整三档尺寸通过实际板卡编码、参考比对和解码验证，缩小仿真本身不作为全高清上板证据。

## 2026-09-18 实际达芬奇结果

三档各连续编码至少 30 秒，测试终点为完整 1920×1080，全部通过。平均帧率基于 FPGA 50 MHz 时钟的相邻帧首像素时间戳，不使用主机解码耗时推算。

| 分辨率 | 验证帧数 | 平均吞吐 fps | 每帧平均输入跨度 ms | 每帧平均描述符结束跨度 ms | 每帧 JPEG 字节数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 640×480 | 134 | 4.450 | 217.329 | 224.663 | 77,189 |
| 1280×720 | 45 | 1.478 | 664.320 | 676.628 | 230,246 |
| 1920×1080 | 20 | 0.666 | 1,482.824 | 1,502.205 | 516,557 |

共验证 199 帧，帧 ID 0–198、124,108,800 个输入像素、31,035,536 字节 JPEG。全部与独立 CPU 参考逐字节一致并能完整解码，状态为零，尺寸和模式有效，时间戳严格递增。每帧输入耗时与完整像素数量的公式吻合；每档 USB 帧率统计之和与实际验证帧数一致，失败帧为零，停止后均有两个完整空闲窗口归零。最后一次统计累计成功数为 199。

当前输出等待比例分别为 98.13%、98.15%、98.13%，输入等待比例约 94.4%，调试传输字节约为 JPEG 的 10.2 倍。三档 JPEG 有效输出速率均约 0.34 MB/s，而带封包的传输速率约 3.5 MB/s。结合受阻周期，当前主要瓶颈是板级调试封包、五字节串行化和异步 USB 输出链路。该结果证明完整 1080p 编码链路可用，不能将 0.666 fps 视为无 USB 背压时编码核的上限，也不代表已经实现真实摄像头的实时全高清采集。

板上保留本版兼容小图测试、实时帧率和数码管的固件，三档测试后已停止，压缩帧率为零。1080p 编码期间一秒窗口的完成数为 0 或 1，因此数码管对应 `000000` 或 `000001`；数码管实物显示外观仍未现场确认，用户不在板卡附近。
