# 1.1.0 吞吐优化记录

本版保持相同的分辨率、质量 85 和模拟图像，对比 1.0.0 的实际板卡吞吐；JPEG 字节、帧序列、FPGA 帧率统计和停止后的归零行为都必须继续验证。

## 实现

新增 `rtl/video/mjpeg_payload_coalescer.v`，将短 JPEG beat 聚合成完整的 16 字节 beat。两个 beat 的本地容量支持余数保留，帧号和通道不同则先排空当前数据；尾部不足 16 字节及时送出。零字节中止标记单独保留，不能与已有数据合并成成功的帧尾。输出受到反压时，数据、有效字节数和帧标记必须稳定。

`mjpeg_synth_top` 增加 `COALESCE` 参数，默认 0 保持模块级原有行为；达芬奇板级测试设为 1。描述符必须等聚合器排空后才进入封包器，以免超过尚未发出的 JPEG 帧尾。原有 32 位封包、五字节串行记录、FPS1/TIM1/END1 和主机接收程序保持兼容。

主机渐进测试默认按完整小包批量读取和解析，避免对每个 32 位字重复调用记录解析与帧重组。遥测仍可能出现在任意字边界，发现控制记录时回退到逐字解析，保留控制事件，并且缓冲回退不会重复保存抓包或增加传输字节统计。`--word-records` 可以使用原逐字路径进行对照。合法字节数、包尾、描述符和 JPEG 帧边界检查保持有效。

16 字节满包含两个 32 位包头和四个数据字，每字仍发送五字节，因此满包传输开销为 30/16=1.875 倍。它尚未达到按大块 JPEG 字节发送时接近 1 倍的有效载荷比例。

`board_test_ft245_async` 的 50 MHz 写时序改为 setup 20 ns、WR# 有效 40 ns、保持 40 ns；WR# 两次脉冲之间的无效间隔至少 80 ns，最短写接收间隔 120 ns（原 220 ns）。读脉宽和恢复时间仍各为 80 ns。根据 [FT232H 官方数据手册表 4.2](https://ftdichip.com/wp-content/uploads/2024/09/DS_FT232H.pdf)，写脉宽至少 30 ns、数据建立和保持至少 5 ns；仍通过同步后的 TXE#/RXF# 决定是否传输。没有更改 FTDI EEPROM。

## 验证入口

```powershell
./mjpeg/scripts/run_progressive_sim.ps1

./mjpeg/scripts/run_mjpeg_board_sim.ps1
python ./mjpeg/host/board_test_receiver.py --capture ./mjpeg/reports/mjpeg_board_test/simulation_fifo/usb_capture.bin --sessions 2 --fps-expected ./mjpeg/reports/mjpeg_board_test/simulation_fifo/fps_expected.csv --output ./mjpeg/reports/mjpeg_board_test/simulation_fifo_coalesced_verified

./mjpeg/scripts/run_core_throughput_sim.ps1

./mjpeg/scripts/run_mjpeg_board_test.ps1 -Action Build

python ./mjpeg/host/progressive_test.py --ftdi --seconds 30 --output ./mjpeg/reports/mjpeg_board_test/hardware_throughput_repeat
```

聚合器测试覆盖字节保持、跨通道/帧号、整包和余数、显式排空、中止标记及反压稳定性。三档缩小控制仿真继续逐帧比对独立 JPEG 参考和测试台独立周期统计。物理 FIFO 行为仿真验证 18 帧、每个写周期的脉宽/建立/保持/恢复、双向总线方向和独立一秒窗口计数；更快的传输结束后仍等待完整计数窗口。

编码核独立仿真使用 `mjpeg_encoder` 原始 128 位 JPEG 接口，连续像素输入、输出 ready 恒为 1，编码两帧完整 1920×1080 渐变图。它测量 50 MHz 下的仿真周期吞吐，须结合 JPEG 参考比对，不直接当作板卡 USB 实测帧率。板级模拟输入目前仍是两周期一个像素。

## 实测结果

首轮上板使用优化固件和原逐字主机解析器，各档至少 30 秒，共验证 1,108 帧。VGA 为 24.683 fps（741 帧），720p 为 8.406 fps（253 帧），1080p 为 3.767 fps（114 帧），约为 1.0.0 的 5.5–5.7 倍；传输开销已降至约 1.875–1.876 倍，但原始输出仍约 3.6 MB/s。证据目录为 `reports/mjpeg_board_test/hardware_throughput_20260918/`。批量主机解析的实际板卡对照另存 `hardware_throughput_batched_20260918/`。

批量解析后的最终上板对照，各档至少 30 秒，新增验证 1,199 帧：

| 分辨率 | 1.0.0 fps | 优化固件＋逐字解析 fps | 优化固件＋批量解析 fps | 相对 1.0.0 | 最终验证帧数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 640×480 | 4.450 | 24.683 | 26.732 | 6.007 倍 | 802 |
| 1280×720 | 1.478 | 8.406 | 9.195 | 6.223 倍 | 276 |
| 1920×1080 | 0.666 | 3.767 | 4.010 | 6.019 倍 | 121 |

主机批量解析在相同固件上进一步提高约 6.5%–9.4%。最终传输开销分别为 1.87606、1.87536、1.87516 倍，原始输出约 3.87–3.97 MB/s，有效 JPEG 输出约 2.06–2.12 MB/s。两轮实际板卡总计验证 2,307 帧，全都与相同尺寸/质量的独立参考逐字节一致并可解码；每帧覆盖完整像素数量，帧号连续，输入和成功窗口计数与帧数一致，失败帧为零，停止后均验证两个完整空闲窗口归零。最终累计成功数为 2,307；板上保留本版固件，输入已停止，数码管预期为 `000000`。

汇总与构建源哈希校验保存在 `build_20260918_115209/throughput_hardware_evidence.json` 和 `HARDWARE_THROUGHPUT_PASS.txt`。两份原始 USB 抓包分别为 326,972,757 和 352,517,677 字节，均与解析结束偏移一致并已关闭。样图与 1.0.0 的同尺寸 JPEG 哈希相同，采用已有视觉结论，不重复打开大图。

编码核独立仿真两帧 JPEG 均与参考完全一致并能解码，50 MHz 下平均输入跨度 42.110 ms、描述符完成跨度 42.430 ms，约 23.568 fps（48.871 Mpix/s），输入等待比例约 1.515%。它使用连续一周期像素输入和始终可接收的原始输出，与板级两周期像素输入和 USB 背压条件不同；只用于判断编码核在这幅图案、质量和供给条件下的能力。证据目录为 `reports/mjpeg_board_test/simulation_core_throughput/`。

优化固件构建为 `build_20260918_115209/`，bitstream SHA-256 为 `a68d494818c91721d610dea6c9484d419c8d04c8e2beba27c7b728f072b1b955`。50 MHz 路由后 setup slack +6.530 ns、hold slack +0.048 ns；DRC 0 错误、66 个已有 RAM/DSP 警告。资源为 12,375 LUT（59.50%）、17,804 FF（42.80%）、25 BRAM（50%）、42 DSP（46.67%）。已经实际 JTAG 下载，配置 CRC=0、DONE=1、EOS=1。

历史对照为 VGA 4.450 fps、720p 1.478 fps、1080p 0.666 fps；板卡对比使用相邻帧的 FPGA 时间戳，输入/输出等待比例有重叠，不能相加。测试期间数码管继续显示板内一秒窗口成功帧数，数码管外观仍未现场确认。

## 后续方向

继续减少 32 位小包及五字节记录开销，增加大块传输和缓存；结合本版实测区分主机解包、异步 FIFO 及编码核限制。高速同步 FIFO 和一周期像素输入需要继续评估。当前异步接口及输入方式仍有吞吐上限，本版验证不会自动代表真实摄像头已经能无损接入或实现原方案双路 1080p60。

本版解决了短 beat 导致的约 10.2 倍封包膨胀，整体吞吐提高约 6 倍。当前仍是调试传输链路主导；输出等待比例约 98% 的统计点是 32 位封包字接口，包含每字串行化和 USB 等待，不能据此承诺去除等待就能提高 50 倍。实际板卡原始输出约 4 MB/s，尚未分开统计 TXE# 等待与主机处理时间，因此不能将剩余限制全部归因于某一个环节。板内模拟输入两周期一个像素的理想上限为 25 Mpix/s，即 1080p 约 12.06 fps；后续接近该吞吐时也需要优化输入。
