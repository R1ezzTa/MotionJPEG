# OV5640 真实摄像头输入

后续高清与帧率测试见 [单路 OV5640 渐进验收](OV5640渐进验收.md)。本文保留第一版 VGA15 的接入证据；新构建脚本支持静态 CameraProfile 0–5，高清档位的实际通过情况以渐进报告为准。

## 第一版范围和验证边界

项目只实现一颗摄像头的单路采集、单路 FPGA JPEG 编码及 USB 输出，主机负责接收与显示。分档性能和带宽指标均按单路评估；多路并发不属于本项目目标。当前编码核已经配置 `CHANNELS=1`。

本次工作区在 1.2.0 编码核心上增加真实 OV5640 输入，第一版固定 **640×480、YUV422 YUYV、实测约 15 fps**。编码和封包时钟为 **100 MHz**，FT232H 同步 USB FIFO 时钟为 **60 MHz**。原渐变源 288.8 fps 等结果不代表摄像头帧率。

2026-09-26 已经通过 JTAG 下载到实际达芬奇 A35T，并经 USB_SLAVE 接收真实摄像头图像。10 秒接收与设备重开后 3 秒接收合计 **189 帧 JPEG 全部独立解码成功**。这属于短时接入验收；长期运行、不同场景和 Ubuntu 主机仍需验证。

## 数据路径

```text
OV5640 8 位 DVP，Y0 U0 Y1 V0
  → PCLK 域采集、16 位像素组装及 SOF/EOL/EOF
  → 4096 项异步像素 FIFO（含帧/行标志）
  → 100 MHz MJPEG 核
  → 1 KB MBLK 封包、USB 跨时钟 FIFO
  → FT232H USB_SLAVE
  → Windows / Ubuntu 接收、独立解码与保存
```

这是流式 FIFO 方案，未加入 DDR 完整帧缓存。摄像头没有 `ready` 反压信号；只在新帧边界决定准入，编码器忙时可以跳过整帧。格式错误或 FIFO 溢出触发清空及 abort，未完成的 JPEG 由失败描述符报告，之后恢复下一帧。4096 项 FIFO 能吸收短时停顿，不能承诺任意时长的 USB 阻塞期间不丢帧。

## 摄像头连接和格式

使用兼容达芬奇板载摄像头接口、带 24 MHz 模块时钟的 DVP OV5640 模块。数据由板载专用摄像头排针进入，`USB_SLAVE` 用来向主机输出 JPEG；`USB_UART` 不承担摄像头图像输入。

实际管脚见 `constraints/davinci_mjpeg_board_test.xdc`，与参考表 `constraints/reference/DaVinci_FPGA_IO.xdc` 对应：DATA[7:0]、PCLK、HREF、VSYNC、SCL/SDA、RESET/PWDN。当前采集按 PCLK 上升沿取样、HREF/VSYNC 高有效处理，OV5640 配置 `0x4300=0x30`、`0x501f=0x00` 为 YUYV。编码核每个 16 位输入字的低字节为 Y，高字节按偶/奇像素交替为 Cb/Cr。

此版未实现动态分辨率切换。`C` 启动固定 VGA，`V` 保留为兼容命令；不要用历史渐进测试中的 H/F 命令期望得到真实 720p/1080p。后续提高分辨率需要同时调整摄像头寄存器、DVP 尺寸、输入时序约束和缓存，而非仅修改主机 `--width/--height`。

## SCCB 初始化和状态

`rtl/camera/ov5640_init.v` 控制电源/复位时序，使用约 100 kHz SCCB 读取 `0x300a/0x300b`，期望芯片 ID 为 `0x5640`。然后写入 VGA/YUV422 寄存器表并读回关键格式、尺寸和时钟相关寄存器。失败时停止初始化并设置 `init_error`，状态仍能通过 USB 发送，不需要先产生图像。

MBLK 类型 7 的 body 为 **32 字节、8 个 little-endian 32 位字**：

| 字 | 主机字段 | 含义 |
|---|---|---|
| 0 | `flags` | bit0 `init_done`；bit1 `init_error`；bit2 `capture_active`；bit3 `tables_ready`；bit4 `codec_busy`；bit5 `config_error`；bit6 `streaming`；bit8 `light_requested`；bit9 `light_on`；bit10 `light_error`；bit11 `light_busy` |
| 1 | `chip_id` | 低 16 位为 SCCB 读出的芯片 ID |
| 2 | `config_index` | 当前初始化操作索引；0/1 为 ID 读取，2–261 为寄存器写入，262 起为关键寄存器读回 |
| 3 | `pclk_ticks` | 自复位以来 PCLK 累计计数 |
| 4 | `received_frames` | DVP 已准入且完整采集的帧数 |
| 5 | `dropped_frames` | 未准入的整帧，以及采集错误丢弃的帧；包括 idle/stop/busy 的有意跳帧 |
| 6 | `overflow_count` | 像素 FIFO 溢出次数 |
| 7 | `dvp_byte_count` | 所有 HREF 有效且 VSYNC 无效的 DVP 字节，包括未准入帧 |

状态约每秒发送，也在 idle 和初始化失败时发送。PCLK 域计数经 Gray 编码同步到核心域，各字段存在同步延迟。计数为 32 位、会自然回绕；主机增量按模 2³² 计算。状态包没有采样时间戳或窗口号，不能据此宣称测得精确 PCLK 频率。

`ack_error_count`、`last_reg_addr`、`init_error_code` 在初始化模块内可用于 ILA，但本版 32 字节 USB 状态没有携带它们。主机可定位失败阶段，不能仅凭 `init_error` 区分 NACK、ID 不匹配和寄存器读回不匹配的具体原因。

## 构建、下载和主机接收

当前 `scripts/build_mjpeg_board_test.tcl` 和工程导入脚本使用 `REAL_CAMERA=1`；模块的默认参数仍保留模拟源模式供旧测试台回归。构建和下载沿用现有工具：

```powershell
./mjpeg/scripts/run_mjpeg_board_test.ps1 -Action Build
./mjpeg/scripts/run_mjpeg_board_test.ps1 -Action Program
```

主机使用 Python 3.10+、Pillow 和 FTDI D2XX；Ubuntu 的 D2XX 安装及实际回读仍需在目标主机验证。下载器和 USB_SLAVE 是两条独立连接。

```powershell
python mjpeg/host/camera_receiver.py --ftdi --duration 10 --output mjpeg/reports/ov5640/hardware_live

# 不连接硬件，重放抓包并独立验证真实 JPEG。
python mjpeg/host/camera_receiver.py --capture mjpeg/reports/ov5640/hardware_live/usb_capture.bin --output mjpeg/reports/ov5640/verified_offline
```

脚本打开 FT232H 同步 FIFO，发送 `C`，等待 MBLK 类型 6 `START`。持续接收 JPEG 类型 0 和类型 1 描述符，以及类型 2 FPS、类型 3 帧计时、类型 4 链路计数和类型 7 状态。持续时间到后发送 `S`，板卡停止新帧准入，排空当前帧、描述符和遥测，再发送类型 5 `END`。无图像时也按时发送 `S`，超时保存诊断后报告失败。

FTDI 设备重开会通过 USB 时钟保护复位设计，使初始化和帧号重来。不要同时运行两个主机接收进程。首帧 ID 可自动接受，之后必须连续；未准入的摄像头帧不会消耗编码帧号。数码管继续显示每秒成功压缩帧数，可能与输入传感器帧率不同。

补光灯使用 OV5640 STROBE GPIO。`L` 请求一次约 2 秒点亮，`l` 或 `S` 请求关闭；FPGA 自行计时关灯，运行期间无需主机持续发命令。初始化保持灯灭。开关均检查 SCCB ACK 并读回 `3019`；持续 NACK 或读回错误会拉低摄像头 RESET 并报告 `light_error`。`light_on` 表示寄存器读回确认，不是光照传感器检测。主机短时试灯命令：

```powershell
python mjpeg/host/camera_receiver.py --ftdi --duration 8 --light-pulse --light-after 2 --save-count 120 --output mjpeg/reports/ov5640/light_test
```

脚本先收到真实帧，再发送一次 `L`，通过后续状态检查开灯及自动关闭。2 秒时不发送 `l`，用于验证 FPGA 自行关灯；停止和异常清理时另外发送 `l`。官方指南第 1254–1255 页说明 LED 功率较高，不宜持续点亮。本版硬件定时上限固定，若需要更长照明，应先核实模块散热和 LED 连续工作能力。

真实图像不与渐变图案或固定 JPEG 参考逐字节比较。脚本对每个成功 JPEG 用 Pillow 完整解码，检查描述符尺寸、长度、状态、连续帧号和递增时间戳。失败描述符仍保存，并继续接收以检查后续恢复；整个测试最后报告失败。保存文件包括：

- `usb_capture.bin`：原始 USB 抓包，可离线重放。
- 前五个 `camera0_frame*.jpg`：接收到的真实 JPEG；数量可用 `--save-count` 修改。
- `frames.json`、`fps.json`、`timings.json`、`link_windows.json`、`camera_status.json`。
- `summary.json`：验证状态、失败原因、摄像头诊断提示、JPEG 大小和带宽统计。

## 无图像诊断

以下仅为状态推断，应结合引脚测量或 ILA 判断：

| 观察 | 优先检查 |
|---|---|
| `init_error=1`，索引 0/1 | SCCB 接线、模块供电/时钟、复位和芯片 ID |
| ID 为 0x5640，初始化停在寄存器阶段 | 该阶段 SCCB ACK 或关键寄存器读回；具体错误需 ILA |
| 初始化完成，连续状态中 PCLK 计数不动 | 摄像头时钟、DVP 输出使能、PCLK 管脚连接 |
| PCLK 计数增加，有效字节不增加 | HREF/VSYNC 极性、连接、摄像头输出配置 |
| 有效字节增加，完整采集帧不增加 | 帧准入、行长/帧高设置、同步格式错误 |
| `overflow_count` 增加 | 编码或 USB 反压是否超过短时 FIFO 的缓冲能力 |
| 完整采集帧增加，但 JPEG 为零 | 编码状态、失败描述符、封包与 USB 输出 |
| 只有 `dropped_frames` 增加 | 先判断是否 idle/stop/busy 有意跳帧，不能直接认定 FIFO 溢出 |

## 带宽评价口径

VGA YUV422 每帧原始数据为 640×480×2 = **614,400 字节**，15 fps 对应 **9.216 MB/s**（十进制 MB）。这是尺寸和帧率的计算值，本次 DVP 有效字节计数增量也与该码率一致。

收到真实 JPEG 后，以全部成功帧的原始字节总量除以 JPEG 总量评价压缩比；带宽降低比例为 `1 - JPEG总量/原始总量`。脚本同时报告 JPEG 每帧大小的均值、P95、最大值，并用默认目标 15 fps 计算 JPEG 数据码率。`--target-fps 30` 可评价另一帧率下的码率，但不会改变摄像头配置。

`timestamp_fps` 根据第一帧到最后一帧的板端时间戳和 100 MHz 核心时钟计算，表示接收并成功解码的帧率。`wire_bytes` 包含 MBLK 头、描述符和遥测，不包含 USB 总线事务开销。不能把历史渐变图约 8:1 的压缩比当作真实场景保证；应使用光线、纹理和运动不同的画面评估峰值码率。
