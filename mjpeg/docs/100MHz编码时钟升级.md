# 100 MHz 编码时钟升级

达芬奇 A35T 的板载 50 MHz 晶振通过 `MMCME2_BASE` 倍频：输入周期 20 ns，DIVCLK_DIVIDE=1、CLKFBOUT_MULT_F=20、CLKOUT0_DIVIDE_F=10，VCO 为 1000 MHz，编码和封包域为 100 MHz。反馈和输出均经过 BUFG。FT232H 控制器继续使用芯片 CLKOUT 的独立 60 MHz 时钟；图样、质量 85、单周期像素输入和 MBLK 协议保持一致。

`davinci_mjpeg_board_test_top` 默认 `CLOCK_HZ=100000000, USE_MMCM=1`。MMCM 的 LOCKED 参与复位，时钟保护超时调整为 100,000 个编码周期，仍为约 1 ms。帧率窗口、数码管扫描和时间戳同步改按 100 MHz 计时。仿真的 `USE_MMCM=0` 仅供旧版异步设计回归；只修改 CLOCK_HZ 参数不会改变真实硬件频率。

## 时序与跨时钟约束

板载输入时钟继续约束为 20 ns，Vivado 从 MMCM 自动推导 10 ns 编码时钟。构建脚本检查 TX FIFO 写指针的真实时钟周期，必须为 10 ns；采用 Explore 布局布线和 AggressiveExplore 物理优化，完整路由建立、保持、复位恢复、CDC、bus skew 和 DRC 检查通过后才生成 bitstream。

100 MHz 发出的 TX 写指针和 RX 读指针 Gray 总线，最大传输延迟及偏斜收紧为 10 ns；60 MHz 发出的指针仍为 16.667 ns。原子快照保持至应答，数据总线最大延迟为 10 ns。USB DATA/WR#/RD#/OE# 的外部时序及三态释放的独立 8 ns 上限沿用同步 FIFO 版本。

首次 100 MHz 完整构建 `build_20260918_204919` 的域内建立裕量为 +0.008 ns、复位恢复裕量 +0.117 ns，但 RX FIFO 的八位分布式 RAM 写时钟到读寄存器路径被当作固定相位同步路径，产生 -4.187 ns 超限，未下载该构建。两组时钟独立，不能以其 STA 假定的相位关系判断这组数据路径。

RX FIFO 只有在写指针经过 wgray_r1、wgray_r2 同步后，才允许读取新写入位置：最早捕获新数据的边沿距源写入至少两个完整编码周期。相应 RAM CLK→m_data 路径单独设置 `set_max_delay -datapath_only 10.000`，给数据留出一个完整编码周期的稳定余量；RAM 读地址到数据寄存器的路径仍检查普通单周期时序。该约束限定具体 RAM 时钟和八个读寄存器，并检查端点存在，不对时钟组整体设置 false path。

MMCM 参数和自动派生时钟依据 [AMD MMCME2_BASE 文档](https://docs.amd.com/r/2021.1-English/ug953-vivado-7series-libraries/MMCME2_BASE)、[自动派生时钟说明](https://docs.amd.com/r/en-US/ug903-vivado-using-constraints/Automatically-Derived-Clocks)。USB 时序依据 [FT232H 数据手册](https://ftdichip.com/wp-content/uploads/2024/09/DS_FT232H.pdf)。

## 仿真验证

MMCM 官方仿真模型实际锁定并输出 10 ns 周期，测试台逐边沿独立检查；两轮小图共 18 帧和三档缩小尺寸渐进共 6 帧，均匹配参考并成功解码，FPS、逐帧耗时和 USB 物理写入计数与独立 TB 完全一致。缩小尺寸仅验证逻辑，不作为全分辨率吞吐结果。100 MHz 写入、60 MHz 读取的 FIFO 压力测试通过 20,136 字节保序、1,258 次绕回、36,205 个满缓冲阻塞周期，覆盖满队列复位、无 USB 时钟、暂停/恢复和前端反压保持。主机协议及初始化的 13 项检查通过；将旧 50 MHz 抓包故意按 100 MHz 换算，主机正确拒绝其 288.813 fps 与板内 144.414 fps 的冲突。

## 实板结果（2026-09-18）

达芬奇 A35T，Windows D2XX，完整彩色渐变、质量 85；逐帧实时核验和仅接收各运行三档、每档 30 秒。仅接收抓包随后全部逐帧离线核验。

| 分辨率 | 50 MHz 同步 fps | 100 MHz 实时 fps | 100 MHz 仅接收 fps | 提升 | 实时验证帧数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 640×480 | 144.407 | 288.813 | 288.813 | 2.000× | 8,665 |
| 1280×720 | 48.420 | 96.841 | 96.841 | 2.000× | 2,906 |
| 1920×1080 | 21.605 | 43.209 | 43.209 | 2.000× | 1,297 |

两轮完整分辨率共 **25,736 帧**逐字节匹配 CPU 参考并成功解码，JPEG SHA-256 与 50 MHz 同步版一致。各阶段帧号连续，停止后两次零 FPS 窗口通过，板内一秒压缩计数与 100 MHz 时间戳换算一致。另有首批小图 27 帧及积压恢复后 27 帧通过，共 **25,790 帧实板 JPEG** 完成核验。

积压恢复测试中，250 ms 不读 USB 后驱动已有 65,536 字节；关闭、重新选择同步模式后，G 会话恢复帧号 0..26，全部匹配参考并解码，无旧封包混入。EEPROM word0 仍为 0x0011。

最终构建 `build_20260918_211617` 的全局建立/保持裕量 **+0.064/+0.012 ns**，100 MHz 域内建立裕量 **+0.742 ns**，编码域复位恢复裕量 **+1.109 ns**；关键 CDC 违例为零，Gray bus skew 通过，DRC 0 错误，保留原有 66 个流水线/RAM 异步控制警告。资源：LUT 64.44%、寄存器 48.56%、BRAM 57.00%、DSP 46.67%；使用 1 个 MMCM、3 个 BUFG。JTAG 状态 DONE=1、EOS=1、CRC ERROR=0。

## 提频后的限制

1080p 稳态线路写入 **22.586 MB/s**。60 MHz 链路周期中，有效写入 37.64%、写准备 0.07%、TXE 等待 7.82%、上游无字节 54.46%。一帧喂入平均 22.948 ms，100 MHz 单周期源理想时间 20.736 ms，输入等待 9.64%。

100 MHz 单像素源的 1080p 理论上限为 48.225 fps，实测达到其 89.6%。仅接收比实时参考比对/解码的帧率变化为 0.0000%，主机 CPU 时间占比从 66.2% 降至 12.0%（以一个 CPU 核时间计）。仍主要受编码域到封包模块的供给限制；USB TXE 阻塞有所增加，但不是当前主瓶颈。现有计数不能把等待进一步归因到某个编码级，编码输出握手等待也不等于 USB TXE 阻塞。

数码管继续显示每个真实一秒窗口成功压缩的整数帧数；驱动和独立事件计数已通过仿真，现场显示外观仍待确认。测试结束后已停止连续编码，板卡保留 100 MHz 同步固件的临时 JTAG 配置。

## 重跑方法

在仓库根目录运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File mjpeg/scripts/run_import.ps1 -BoardTest
powershell -NoProfile -ExecutionPolicy Bypass -File mjpeg/scripts/run_sync_fifo_sim.ps1
python -m unittest discover -s mjpeg/tb -p 'test_*.py'
powershell -NoProfile -ExecutionPolicy Bypass -File mjpeg/scripts/run_mjpeg_board_test.ps1 -Action Build
powershell -NoProfile -ExecutionPolicy Bypass -File mjpeg/scripts/run_mjpeg_board_test.ps1 -Action Program
python mjpeg/host/board_test_receiver.py --ftdi --blocks --sync-fifo --sessions 3 --output mjpeg/reports/mjpeg_board_test/hardware_core100_small_20260918
python mjpeg/host/progressive_test.py --ftdi --blocks --sync-fifo --pixel-cycles 1 --core-clock-hz 100000000 --seconds 30 --output mjpeg/reports/mjpeg_board_test/hardware_core100_live_20260918
python mjpeg/host/progressive_test.py --ftdi --blocks --sync-fifo --pixel-cycles 1 --core-clock-hz 100000000 --receive-only --seconds 30 --output mjpeg/reports/mjpeg_board_test/hardware_core100_receive_20260918
python mjpeg/host/progressive_test.py --capture mjpeg/reports/mjpeg_board_test/hardware_core100_receive_20260918/usb_capture.bin --blocks --sync-fifo --pixel-cycles 1 --core-clock-hz 100000000 --output mjpeg/reports/mjpeg_board_test/hardware_core100_receive_20260918/verified_offline
python mjpeg/host/sync_recovery_test.py --output mjpeg/reports/mjpeg_board_test/hardware_core100_recovery_20260918
```

100 MHz 固件及其渐进抓包必须带 `--core-clock-hz 100000000`，否则时间戳帧率和耗时将按旧 50 MHz 错算。默认 50 MHz 保留以兼容历史抓包；主机还将时间戳帧率与板内一秒窗口独立比较，发现明显不一致即报错。缩放窗口的仿真用 `--simulation`，不将其窗口误当作真实一秒。

同步主机程序每次打开设备会触发时钟保护复位，帧号从零开始；同一进程内三档连续。Windows 实机验证与 Ubuntu 的接收入口分开记录，Ubuntu 尚未实机测试。下载仅使用 JTAG 易失配置，不写 Flash 或 FTDI EEPROM。
